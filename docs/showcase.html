Chunk

~512-char passages with overlap, so a fact split across a boundary still lands whole in one chunk.

Filter

noise removal

Drops tables-of-contents, reference lists and number grids, close to queries, but they answer nothing.

Embed

Text becomes 1024-dimension vectors; queries get BGE's instruction prefix for sharper retrieval.

Experiment · chunk size

The same eight questions, re-run at two chunk sizes, the classic RAG trade-off, measured rather than guessed.

512, richer contextrelevance 75% · 12.5s
256, fasterrelevance 69% · 6.3s

Same recall either way, both find the key facts. Smaller chunks nearly halve latency; larger chunks give the model more to reason over. One env var to switch.

Decisions

The choices that made it work.

Rerank the shortlist

Vector similarity is fast but coarse. A cross-encoder reads the question and each candidate together, the sharpest single jump in quality after clean chunks.

Filter the noise

On real PDFs, contents pages and bibliographies look relevant to the embedder but answer nothing. Dropping them was the line between garbage and grounded.

Persist the index

Embedding a long PDF is the expensive step, so the index and a folder fingerprint are saved, restarts are instant, and only changed files are re-embedded.

Stay local

Ollama and sentence-transformers keep Ember private, free and fully inspectable. The goal was to understand the internals, not to call an API and hope.
